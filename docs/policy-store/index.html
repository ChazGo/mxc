Proposed MXC SDK feature

A shared floor, not a shared mutable policy

Proposed MXC SDK APIs resolve reviewed, statically bundled requirements for known tools into an MXC SandboxPolicy. Each consumer owns lookup, authorization, composition, persistence, audit, and sandbox creation. The floors are best-effort compatibility data, not a guarantee that a workflow succeeds. Learning Mode complements them by discovering requirements the bundled catalog does not yet describe.

Proposed MXC SDK API - pending API review

MXC SDK APIs return the existing policy type

A consumer explicitly passes one tool or an array. The MXC SDK resolves each tool-plus-intent pair from its bundled V1 catalog and returns one composed SandboxPolicy, or undefined when no pair contributes. resolveSandboxPolicyWithDiagnostics adds attribution and per-input statuses. Package URL is the strong identity; invocation name is the explicitly enabled fallback. The APIs are proposed and pending API sign-off before check-in. Their names may change during review, including removal of "Sandbox" to align with MXC naming.

Ownership boundary

What the catalog owns and what each agent owns

Shared and read-only

MXC SDK and bundled catalog

  • Known-tool requirement catalog bundled with the SDK release
  • Catalog schema, validation, and integrity digests
  • Identity, version, platform, architecture, and intent resolution
  • Dependency closure plus filesystem and network floor composition
  • Proposed TypeScript, Rust, and .NET SDK APIs
  • Lookup diagnostics and catalog inspection

The APIs and static V1 data live in the MXC repository and ship in the existing SDK packages. The Rust mxc_policy_store core performs resolution; Node and .NET wrap it through mxc_ffi. They are targeted for a later release after MXC 1.0, with a catalog schema that remains compatible within MXC 1.x. Lookup is an SDK API, not a hosted service or CLI. .NET failures use MxcException with a Reason property for an optional stable catalog-specific reason.

Consumer-specific and writable

Agent policy store and UX

  • Access profile and default posture
  • Whether catalog lookup is enabled at all
  • Accepted-floor persistence with catalog and entry revisions
  • User changes and per-tool overrides
  • Learning Mode candidates and approvals
  • One-time and persistent authorization
  • Settings UI, audit data, and migration

The agent composes the final request without exceeding OS, enterprise, or device constraints.

Proposed data flow

From reviewed requirement to contained execution

Every entry has one conservative default. Resolution applies only additive overlays, then selects intent.

1. Default Conservative common floor Required once per entry, with base policy and common intents.
+
2. Host overlay Platform + architecture At most one matching overlay using additive catalog fields.
+
3. Version overlay Zero or one VERS range Non-overlapping, additive, and parsed with the entry's required scheme.
+
4. Intent Named operation or all A named intent must exist; omission selects every effective intent.

effective policy = default + platform/architecture additions + at most one version variant + selected intent

Identity and version selection

One deterministic result per requested pair

packageUrl is the strong identity and invocationName is the fallback. Invocation names compare case-insensitively on Windows and macOS, and exactly on Linux. Each entry declares versionScheme as npm, semver, pypi, nuget, or intdot.

Illustrative Git entry

Small overlays, complete rendered review

DefaultRead Git; read/write project; fetch and push.
WindowspolicyAdditions adds read access to ${programData}/Git.
>=2.40 <2.50intentAdditions adds the SSH dependency only to default-declared push.
>=2.50 <3newIntents defines bundle-fetch, its cache path, and its HTTPS rule.

Git 2.45 + push includes the default, Windows path, push rule, and SSH dependency. Git 2.55 + bundle-fetch includes that newer intent but not the other range's SSH addition. With no version, bundle-fetch is unsupported and contributes no base policy.

Overlays use policyAdditions for base access, intentAdditions only for intents declared by the default, and newIntents only for new names. Publication materializes every platform × architecture × version × intent policy, validates it against the MXC schema, proves the default is a subset, rejects overlapping ranges or narrowing operations, and produces a rendered view for reviewers.

Composition across contributing pairs

Satisfy every selected requirement, never a broader approximation

A tool with no network need does not veto another tool's scoped network requirement. Read-write supersedes overlapping read-only access. A catalog filesystem deny or egress deny that overlaps required access from any selected tool-plus-intent pair is removed in full; diagnostics name its full scope and the contributing entries. Non-overlapping catalog denies remain, and an overlapping catalog egress deny is never a composition conflict. Caller-owned restrictions remain authoritative. If other selected requirements cannot be represented by the defined filesystem and network rules, resolution fails instead of granting broader access.

A dependency contributes only its unversioned default base plus applicable platform base additions. It contributes no intents unless the reference explicitly names them, for example { entryId: "tool:ssh", intents: ["connect"] }. A named dependency intent that is missing from any applicable materialized platform combination fails catalog validation.

  1. 1

    Capture or declare requirements

    Contributors gather evidence about what a tool needs, for example with MXC learning-mode capture before opening a pull request. Nothing is submitted at runtime.

  2. 2

    Review and bundle a catalog entry

    The common default and add-only overlays are generalized, materialized, validated, and reviewed, then included in an immutable catalog revision bundled with an SDK release. Corrections ship in a later bundled revision.

  3. 3

    Resolve through the MXC SDK

    On an explicit call, the SDK selects one entry per input, applies its default and additive overlays, selects intent, resolves dependencies and symbols, and composes contributing pairs. Lookup is local: it never runs the tool or downloads policy data.

  4. 4

    Apply consumer policy and approval

    The agent evaluates the floor against its access profile, user configuration, learned overrides, and approval rules.

  5. 5

    Respect non-overridable ceilings

    OS, enterprise, device, and caller-owned restrictions remain authoritative. Catalog composition never removes them.

  6. 6

    Create and audit the sandbox

    The consumer creates the final MXC request and records the catalog revision, contributing entries, warnings, approvals, and effective policy.

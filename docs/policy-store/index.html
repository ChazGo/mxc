Proposed design

A shared floor, not a shared mutable policy

MXC provides a reviewed, versioned, read-only catalog describing the minimum sandbox requirements associated with known tools. Each consuming agent owns its user settings, learned changes, approval experience, policy composition, persistence, and final sandbox creation.

Stored policy for tool?

OpenClaw first checks its writable per-tool policy store. An existing record avoids a catalog lookup. A missing record checks whether automatic MXC floor retrieval is enabled before selecting either the catalog path or the configured default preset. 

policyStore.get(toolId)

Ownership boundary

What MXC owns and what each agent owns

Shared and read-only

MXC policy store

  • Known-tool requirement catalog
  • Catalog schema and validation
  • Versioning and dependency resolution
  • SDK lookup and diagnostics
  • Integrity and packaging model

MXC returns requirements. It does not decide what the user permits.

Consumer-specific and writable

Agent policy store and UX

  • Access profile and default posture
  • Per-tool floor persistence and matching
  • Automatic floor retrieval setting, enabled by default
  • User changes and per-tool overrides
  • Learning Mode candidates and approvals
  • One-time and persistent authorization
  • Settings UI, audit data, and migration

The agent composes the final request without exceeding OS, enterprise, or device constraints.

First consumer in the current proposal

OpenClaw

Calls the MXC API once for each tool by passing a single-element tools array. OpenClaw stores each returned floor separately when automatic retrieval is enabled. Users can opt out and apply the selected default MXC preset directly without storing it for the tool. OpenClaw owns the mutable configuration, approvals, audit data, and final sandbox composition.

Extensible contract

Other agent runtimes

Any consumer can use the catalog if it can identify tools, evaluate the returned requirements, apply its own authorization model, and create an MXC sandbox.

Proposed data flow

From reviewed requirement to contained execution

  1. 1

    Capture or declare requirements

    Maintainers gather evidence about the files, network endpoints, runtimes, and capabilities a tool needs.

  2. 2

    Review and publish a catalog entry

    The requirement is generalized, validated, versioned, and reviewed before it becomes catalog data.

  3. 3

    Resolve through the MXC SDK

    The resolver matches tool identity, follows dependencies, resolves symbols, and returns a sandbox policy floor or undefined. OpenClaw stores a returned floor per tool; undefined uses the selected default MXC preset.

  4. 4

    Apply consumer policy and approval

    The agent evaluates the floor against its access profile, user configuration, learned overrides, and approval rules.

  5. 5

    Respect non-overridable ceilings

    OS, enterprise, and device constraints remain authoritative even when a tool floor requests broader access.

  6. 6

    Create and audit the sandbox

    The consumer creates the final MXC request and records the catalog version, matched entry, approvals, and effective policy.

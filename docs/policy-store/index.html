Proposed public preview

A shared floor, not a shared mutable policy

A proposed catalog, owned outside MXC, describes the minimum sandbox requirements of known tools in reviewed, immutable revisions. Its libraries return the MXC SDK's own SandboxPolicy. Each consumer owns lookup, authorization, composition, persistence, audit, and sandbox creation. It is a temporary bridge until Learning Mode replaces it.

Proposed catalog library API

Standalone libraries return the MXC SDK's policy type

A consumer explicitly passes one tool or an array. The TypeScript, Rust, or .NET library resolves its local catalog and returns that SDK's exact SandboxPolicy, or undefined when nothing matches. resolveSandboxPolicyWithDiagnostics adds attribution and warnings. 

export declare function resolveSandboxPolicy(
  tool: ToolInput,
  ctx?: ResolveContext
): SandboxPolicy | undefined;
export declare function resolveSandboxPolicy(
  tools: readonly ToolInput[],
  ctx?: ResolveContext
): SandboxPolicy | undefined;
export declare function resolveSandboxPolicyWithDiagnostics(
  tool: ToolInput,
  ctx?: ResolveContext
): SandboxConfigResolution;
export declare function resolveSandboxPolicyWithDiagnostics(
  tools: readonly ToolInput[],
  ctx?: ResolveContext
): SandboxConfigResolution;

In this illustrative per-tool flow, the consumer first checks its own writable policy store. An existing record avoids a catalog lookup. A missing record checks whether the consumer has explicitly enabled catalog lookup before choosing the catalog path or its restrictive baseline.

Ownership boundary

What the catalog owns and what each agent owns

Shared and read-only

Proposed catalog project

  • Known-tool requirement catalog in immutable revisions
  • Catalog schema, validation, and integrity digests
  • Matching, dependency closure, and filesystem floor composition
  • TypeScript, Rust, and .NET libraries on real MXC SDK types
  • Lookup diagnostics and catalog inspection

MXC keeps SandboxPolicy and its SDKs and never calls the catalog. The catalog returns requirements, not permission.

Consumer-specific and writable

Agent policy store and UX

  • Access profile and default posture
  • Whether catalog lookup is enabled at all
  • Accepted-floor persistence with catalog and entry revisions
  • User changes and per-tool overrides
  • Learning Mode candidates and approvals
  • One-time and persistent authorization
  • Settings UI, audit data, and migration

The agent composes the final request without exceeding OS, enterprise, or device constraints.

Illustrative consumer OpenClaw

OpenClaw's per-tool configuration RFC defines OpenClaw-owned storage, matching, approvals, audit, and fail-closed enforcement. It does not define catalog lookup or built-in per-tool defaults. The same library contract can support another agent that needs shared known-tool requirements while retaining its own settings and policy experience. A direct catalog integration is not committed by the public design sources.

Extensible contract Other agent runtimes

Any consumer can use the catalog if it can identify tools, evaluate the returned requirements, apply its own authorization model, and create an MXC sandbox.

Proposed data flow

From reviewed requirement to contained execution

  1. 1

    Capture or declare requirements

    Contributors gather evidence about what a tool needs, for example with MXC learning-mode capture before opening a pull request. Nothing is submitted at runtime.

  2. 2

    Review and publish a catalog entry

    The requirement is generalized, validated, and reviewed, then published in an immutable revision. Corrections publish a new revision.

  3. 3

    Resolve through a catalog library

    On an explicit call, the library composes every eligible match and dependency, resolves symbols, and returns the SDK's SandboxPolicy or undefined. Lookup is local: it never runs the tool or uses the network.

  4. 4

    Apply consumer policy and approval

    The agent evaluates the floor against its access profile, user configuration, learned overrides, and approval rules.

  5. 5

    Respect non-overridable ceilings

    OS, enterprise, device, and caller-owned restrictions remain authoritative. Catalog composition never removes them.

  6. 6

    Create and audit the sandbox

    The consumer creates the final MXC request and records the catalog revision, contributing entries, warnings, approvals, and effective policy.
